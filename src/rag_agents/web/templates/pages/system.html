    Что на картинке. Каждая точка — чанк (кусок книги ~400 токенов). В Qdrant у неё вектор из 1024 чисел: его посчитала модель bge-m3. Вектор нельзя нарисовать, поэтому метод главных компонент (PCA) проецирует 1024 измерения на 2 оси, вдоль которых точки различаются сильнее всего. Близкие точки близки по смыслу, но проекция теряет много информации, так что соседство на плоскости приблизительное.

    Во время вопроса на карте появится ★ — вектор вашего вопроса в той же проекции, а найденные Qdrant чанки подсветятся кольцами с score (косинусная близость в полных 1024 измерениях, а не расстояние на картинке).

    Три главных сценария

    📥 Загрузка книги (ingest, асинхронно)

    1. Браузер или API-клиент шлёт файл: txt, fb2, epub, pdf, docx или zip с ними.
    2. web пишет файл потоком в uploads, считает sha256 (дубликаты не грузим).
    3. web → PostgreSQL: строка documents со статусом queued, COMMIT.
    4. Только после коммита задача с одним ID уходит в RabbitMQ, очередь ingest.parse.
    5. worker-ingest захватывает документ (UPDATE … WHERE status='queued' RETURNING), парсит формат, чистит текст и режет его структурным чанкером: чанк не пересекает главу, в начале — заголовок «Книга / Часть / Глава».
    6. Чанки → PostgreSQL, затем фан-аут: по задаче на батч в очередь ingest.embed.
    7. worker-embed: батч → Ollama bge-m3 → upsert в Qdrant (id точки — uuid5, повтор не дублирует). Атомарный +1 к счётчику батчей; последний батч ставит done.
    8. Прогресс → Redis, страница агента опрашивает его каждые 2 с.
    9. beat раз в минуту запускает sweeper: застрявшие документы переотправляются, а упавшие задачи лежат в *.dlq до make dlq-replay.

    💬 Вопрос (синхронно, стримом)

    1. Браузер POST вопроса → web проверяет rate limit в Redis, сохраняет вопрос и пустой ответ в PostgreSQL и возвращает HTML с sse-connect.
    2. Браузер открывает SSE-стрим; генерация стартует при подключении.
    3. Вопрос → Ollama → вектор из 1024 чисел (★ на карте).
    4. Вектор → Qdrant: top-k ближайших чанков только этого агента (фильтр agent_id).
    5. Промпт = правила + персона + пронумерованные чанки + вопрос → DeepSeek со stream=true.
    6. Токены летят в браузер событиями token, пока LLM ещё пишет.
    7. Финал: ответ, цитаты и usage → PostgreSQL, событие done приносит итоговый HTML со ссылками [n].
    8. Трейс уходит фоном в Langfuse, счётчики — в /metrics.

    🎯 Eval-прогон (make eval, ~25 мин)

    1. eval — одноразовый контейнер из того же образа: читает golden-датасет (59 вопросов с эталонным ответом и ожидаемыми главами) и создаёт прогон в PostgreSQL.
    2. Каждый вопрос идёт через тот же QueryService, что и у пользователя: Ollama → Qdrant (20 кандидатов для hit@20) → DeepSeek. В чат ответ не пишется.
    3. Без LLM считаются hit@k, recall@k, MRR (совпала ли глава), верность отказа, валидность цитат, отбита ли инъекция.
    4. LLM-судья (DeepSeek, 3 вызова): faithfulness, context precision/recall, answer relevancy, подтверждает ли источник [n].
    5. Метрики вопроса → eval_items, score-ы → трейс в Langfuse, прогон целиком → Langfuse Datasets.
    6. Итог — markdown-отчёт и страница «Качество»: графики, худшие вопросы, сравнение с прошлым прогоном с 95 % CI (парный bootstrap).
